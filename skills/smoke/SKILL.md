## User Input

```text
$ARGUMENTS
```

> 格式：`/smoke [要验证的功能或工单]`
> 示例：`/smoke 镭射打标导出权限`
> 若 `$ARGUMENTS` 为空，从当前上下文（最近改动、打开文件）推断验证目标；无法推断时向用户询问，**不得猜测**。

---

## 适用范围

适用于：功能开发或缺陷修复完成后的写路径验证——走真实业务入口触发，对照接口响应、数据表行变化、日志中真实 SQL 三方证据。单元测试（尤其 mock 掉持久层的）证明不了 SQL 层行为，冒烟的核心增量就是核对真实 SQL，不停留在"理论上对了"。

不适用于：性能压测、前端渲染问题、纯静态代码审查。

---

## 前置约束（不可跳过）

### 只读铁律

本流程对数据库全程只做查询核对，不通过冒烟流程本身修改数据。唯一例外：步骤 5「覆盖缺口」中经用户明确授权选定的直接写库方案。

优先使用已配置的数据库 MCP 工具。仅当没有可用 MCP 工具时才退回 CLI/客户端直连，且必须限定为只读账号或显式加 `--read-only`/等效只读参数；每条 SQL 执行前确认是 `SELECT`，禁止执行来源不明或由用户输入拼接的语句。

### 经验沉淀先行

分别读取两处坑位记录（若存在）：

- `.smoke/pitfalls.md`——全局坑位，跨功能/工单通用。
- `.smoke/<功能或工单>/pitfalls.md`——本功能/工单专属坑位，仅当该功能此前已验证过、留有历史记录时存在。

了解此前踩过的坑，本次核对时留意是否复现。两处文件首次执行、尚不存在时跳过对应部分，不视为异常。

### 确认清单

开始前向用户确认：

- 认证凭据（如项目约定位置里没有，直接问用户要）
- 应用地址、只读数据库查询通道（优先使用已配置的数据库 MCP 工具）
- 应用日志位置（需含真实 SQL 输出，具体日志格式因技术栈而异）
- 服务由谁启动、如何启动（尤其是否为用户本地 IDE 调试进程）

以上各项，先尝试从项目配置/文档/环境变量中查找依据。找到明确依据的直接使用；找不到依据、或找到多个矛盾候选、或属于凭据类敏感信息（即使能找到也应向用户核实是否为当前应使用的），**必须**询问用户。

若执行中遇到 401，向用户说明当前使用的凭据来源、失败的接口/请求，并询问正确凭据，不要反复重试后再零散追问。

## 执行步骤

1. **启动**：按准备阶段确认的方式启动/确认服务运行。默认由用户启动（尤其是 IDE 调试进程），不擅自启停用户的服务进程；代码改动需要重启生效时，告知用户重启，并用启动日志时间戳确认新代码已加载；用户明确授权后才由 agent 自行后台启动。完成标志：服务在运行，且运行的是待验证的代码。
2. **基线**：查相关表现状，调一遍目标读接口比对。完成标志：手握改动前的数据快照。
3. **触发**：走真实业务入口触发写路径。触发前先弄清该入口是否有幂等/去重语义（按天、按单号、按业务 ID；并非所有业务都有）——有才需要据此设计触发方式，且注意重复触发被拦截不代表逻辑正确（如全局或本功能的 `pitfalls.md` 中已记录同类问题，重点核对）。
4. **三对照**：每个触发后查三处——接口响应、数据表行变化、日志中该请求的真实 SQL。SQL 逐条核对子句位置：条件在 ON 还是 WHERE、LIMIT、排序、作用域条件（租户、软删）。完成标志：每个验收点都有接口 + 数据 + SQL 三处证据。
5. **覆盖缺口**：真实入口触达不到的分支，一次性列出全部可行方案让用户统一选择，再为该分支补齐三对照证据。方案包括但不限于：管理端/造数接口准备数据（顺带验证新字段的写链路与落库）、加临时 mock 触发接口（注释标明临时）、直接写库改数据状态（须用户明确授权）、组合已有业务操作凑出前置条件。完成标志：缺口分支有三对照证据。
6. **恢复现场**：一次性向用户列明本次产生的全部数据（测试配置、业务记录、流水等），由用户统一决定删除还是保留，再执行清理；移除临时代码并跑一遍测试。完成标志：工作区无临时改动，测试全绿，数据处置已获用户确认。
7. **产出**：
   - 测试报告写入 `.smoke/<功能或工单>/<主题>-<日期>.md`，内容含：验证范围与验收点清单、每个验收点的三对照证据（接口响应摘要、数据行变化、关键 SQL 摘录）、发现的缺陷与处置、数据残留与处置结论。
   - 若本次发现了新的陷阱/经验，按下方模板追加写入，但需先判断归属，写入对应的一个文件（同一条目不重复写两处）：
     - **具有复现价值的通用性问题**（换一个功能/工单也可能踩到，如某类 ORM 的默认作用域行为、某个中间件的幂等策略、日志采样丢 SQL 等平台级坑）→ 追加进全局 `.smoke/pitfalls.md`。
     - **仅对本功能/工单下次复验有意义的专属信息**（如该接口的隐藏鉴权头、该表的软删字段名、该业务幂等键的组成方式）→ 追加进 `.smoke/<功能或工单>/pitfalls.md`；该文件不存在则按同一模板骨架新建。
   完成标志：报告已落盘且每个验收点可追溯到证据，结论明确（通过/不通过/遗留问题）；新发现的坑位已按归属分别沉淀到全局或功能级 `pitfalls.md`。

## pitfalls.md 模板（全局 / 功能级通用）

`.smoke/pitfalls.md`（全局）与 `.smoke/<功能或工单>/pitfalls.md`（功能/工单级）共用以下骨架。对应文件首次不存在时用骨架创建；后续每次发现新坑/经验/总结，按同一格式追加条目到判断归属后的那一个文件：

```markdown
# 冒烟验证经验沉淀

<!-- 每条格式：
- **[新坑/经验/总结]**：现象是什么、根因是什么、下次核对时该看哪里。（尽量精简）
-->
```
